# 鸿蒙 PRoot 加速和重新进入

> 历史实验记录。命令与结论适用于当时的环境和版本。原始日志与二进制保存在本机。现行结论见[研究索引](../../research/harmonyos-runtime.md)。

基线为 Mate 60 上的 0.4.2，已解包启动至聊天页 195.2 秒，其中 DSH 入口至服务地址 176.1 秒。验证 PRoot seccomp 追踪加速和兼容回退，分别记录 CLI 导入、配置加载、鉴权及页面。保留本机运行与原数据根。重进验收分别覆盖应用仍存活和明确终止进程。涉及强制停止的测试先在独立模拟器执行。

## 实现

- PRoot 在同一 HAP 身份中用 Node、Bash 管道和回环 HTTP 做短探测。只有看到 PRoot 确认追踪加速且三项均成功才选加速，失败记住兼容模式。加速启动在就绪前退出时会重试兼容模式。只影响 PRoot 自己的追踪过滤器。
- 引擎及等待就绪逻辑由应用进程内的单例持有，页面订阅及离开互不影响引擎。PRoot 收到宿主退出信号后结束旧引擎。移除了浏览器启动前重复下载一次首页的请求。
- 启动期间，已知 ESM 源码可从固定 DSH 归档生成的索引加载。ArkWeb 接入后禁用该索引。非索引命中走 Node 原加载器。检查了索引内 9,170 个条目与所用归档逐字节一致。

## 模拟器

0.4.3 第一次安装遇到旧 0.4.2 的残留进程占用 19592，两个模式都没有绑定端口。独立实例重启后，seccomp 探针及 Web 全部通过。0.4.4 的同制品单次对照中，两个样本均确认 seccomp 追踪加速开启。源码索引开启和关闭时，JavaScript 入口到 DSH 公布服务地址分别为 8,007 和 8,035 ms。模块加载器累计读取时间由 1,623 降为 164 ms，整体差异不足以证明改善。强制停止 0.4.3 后旧应用、PRoot 和 Node PID 均消失，重新打开启动了新进程。 索引开（本机产物 `../dsh-client-preview/.build/emulator-0.4.4-packed.log`） · 索引关（本机产物 `../dsh-client-preview/.build/emulator-0.4.4-loose.log`） · 强制关闭（本机产物 `../dsh-client-preview/.build/emulator-force-stop-0.4.3.log`）

## Mate 60

0.4.4 已覆盖安装并加载官方聊天页。签名 HAP SHA-256 为 `ecf3229ca8d566bcc96e790919684e17ad35fc3ffaccb2025b37874fc8b0373a`。真机尝试设置 PRoot 追踪过滤器后，`/bin/node` 在执行入口报错，没有观察到内核向 PRoot 送出可用的加速事件。探针约 165 ms 判失败，自动进入兼容模式。跟踪保留了 prctl 和 execve 位置，暂未证明内核的具体拒绝机制。

0.4.4 从应用开始准备到聊天页约 219.8 s，实际比此前 0.4.2 真机单次样本慢约 24.6 s。这两个真机版本间的数据不构成同制品 A/B。当前只能确认模块读取耗时下降，整体冷启动未证实改善。0.4.4 HTTP 监听本身就到 200 秒，主要等待发生在 DSH Web 配置挂载期间。该阶段剩余时间还需继续区分插件运行、依赖解析和 PRoot 追踪调度。

0.4.4 在真机按 Home 再重开，应用、PRoot 和 Node 三个 PID 完全相同，只有后台／前台事件，未重跑初始化。强制终止类操作结束引擎，冷启动仍是现有瓶颈。此次仅核对本机页面及模拟器启动探针中的 Bash 管道，未发真实模型请求或重新验收 DSH Bash 工具。
